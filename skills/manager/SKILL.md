# 매니저 규약 (새 하네스 P1)

사용자는 레일(태스크·세션)을 직접 관리하지 않는다. 그건 매니저 일이다.
매니저는 계획·배정·감시·검증·보고만 하고, 긴 구현은 직접 붙잡지 않는다. 그래야 사용자와 대화가 끊기지 않는다.

## 0. 상태 파일 (진실의 원천)
대상 프로젝트 루트의 `harness/` 폴더. 없으면 이 스킬 폴더의 `templates/` 를 복사해 만든다.

| 파일 | 내용 | 쓰는 사람 |
| :- | :- | :- |
| `goal.md` | 현재 목표·범위·제약 | 매니저 |
| `tasks.json` | 태스크 목록 (형식은 템플릿 참고) | 매니저가 만들고, 워커는 자기 태스크의 `result_spec`·`notes` 만 수정 |
| `progress.md` | 작업 세션별 한 일 | 워커가 끝날 때 추가 |
| `decisions.md` | 사용자 결정과 근거 | 매니저 |

대화 기록이 아니라 이 파일들로 상태를 이어 간다. 새 매니저 세션이 열리면 먼저 이 네 파일을 읽는다.

## 0-1. 엔진 프로필 (먼저 고른다)
이 문서는 엔진 중립 규약이다. 엔진별 규칙(컴파일·린트 게이트, 심볼 탐색, 플레이 검증, 병렬 제약, 브리프에 넣을 규칙)은 프로필 파일에 있다. 매니저 세션을 시작하면 대상 프로젝트의 프로필을 정해 그 파일을 읽는다.

| 프로필 | 판정 (프로젝트 루트) | 파일 |
| :- | :- | :- |
| unity | `ProjectSettings/` 가 있음 | [profiles/unity.md](profiles/unity.md) |
| roblox | `default.project.json`(Rojo) 이 있음 | [profiles/roblox.md](profiles/roblox.md) |

둘 다 아니거나 애매하면 `harness/goal.md` 의 `profile:` 줄을 따른다. 그것도 없으면 사용자에게 묻는다.

## 1. 요구 정리
- 사용자의 요청을 `goal.md` 에 정리한다. 해석이 여러 갈래면 짐작하지 말고 먼저 묻는다.
- 사용자가 내린 결정은 그때그때 `decisions.md` 에 날짜와 함께 남긴다.

## 2. 태스크 쪼개기
- 태스크 하나는 **워커 한 세션이 30~90분 안에 끝내고 검증할 수 있는 크기**로 잡는다.
- 각 태스크에는 반드시 `success_criteria` 를 둔다. 검증 가능한 문장으로 쓴다 (예: "컴파일 오류 0", "exe 실행 로그에 [Shop] Purchase ok").
- `acceptance` 에는 **착수 전에** 판정 방법을 적는다: `check`(실행할 명령·스크립트), `expect`(기대 결과). 착수 뒤에는 바꾸지 않는다.
- `status` 는 워커 보고가 아니라 **매니저 검증 결과로만** pass/fail 로 바꾼다. 워커는 `notes`·`result_spec` 만 쓴다.
- `depends_on` 이 모두 `pass` 가 된 태스크만 배정한다.

## 3. 워커 배정 (P1: 한 번에 한 명, 순차)
- 데스크톱 앱 세션 시작(`start_session`)으로 워커를 띄운다. 사용자가 맡기라고 했으면 `initiation: "user_asked"`, `context: "fresh"` 를 쓴다.
- 대상 폴더가 이 세션의 폴더가 아니면 `list_start_targets` 로 확인한 `cwd` 를 넘긴다.
- 브리프에는 아래 내용을 모두 넣는다 (워커는 이 대화를 모른다):
  - 프로젝트 경로, 태스크 ID와 제목, 성공 기준
  - 선행 태스크의 `result_spec` (과정이 아니라 결과만 넘긴다)
  - 지킬 규칙: 이 태스크 범위의 파일만 수정
  - 프로필의 "브리프에 넣을 규칙" 절 전부 (게이트·심볼 탐색·테스트 규칙)
  - 같은 분야 경험 기록: `harness/experience/<분야>.md` 가 있으면 최근 10줄 이내를 그대로 붙인다 (다른 분야 기록은 넣지 않는다)
  - 끝날 때 할 일: `harness/tasks.json` 에서 자기 태스크의 `result_spec`·`notes` 갱신(`status` 는 건드리지 않음), `harness/progress.md` 에 한 일 추가(덮어쓰지 않고 이어 쓰기), 막히면 추측하지 말고 매니저에게 메시지
- 배정하면 `tasks.json` 에 `status: "in_progress"`, `worker` 에 세션 id를 적는다.
- P1 에서는 워커가 끝나기 전에 다음 워커를 띄우지 않는다 (에디터·Studio 를 쓰는 검증은 프로젝트당 한 번에 하나. 세부는 프로필의 "병렬 제약").
  - 예외 (2026-10-18 실측): 코드만 다루는 worktree 태스크는 공유 파일 "추가만" 규칙을 브리프에 넣고 2개까지 병렬로 돌렸다. 병합 충돌은 먼저 끝난 쪽을 병합한 뒤 나머지 워커에게 `git merge master` 로 정리시키면 된다.
- **자동 턴 제약**: 워커 보고·서브에이전트 완료 같은 자동 이벤트로 시작된 턴에서는 앱이 `start_session` 을 거부한다. 사용자가 "끝까지 진행"을 원하면 그 턴에서는 백그라운드 서브에이전트(Agent, `run_in_background`, 같은 브리프 + 절대 경로)로 대체한다. 서브에이전트에는 worktree Stop 게이트가 붙지 않으므로 매니저가 병합 전에 게이트를 반드시 재실행한다.

## 3-1. 워커 모델·effort 사다리 (2026-10-17 확정, 근거: kano/docs/harness-research/findings.md "워커 모델·effort" 절)
`start_session` 의 `model`·`effort` 로 시작 시 정한다. 세션 중 모델은 바꾸지 않는다(캐시 깨짐). effort 는 5.5 에서 세션 중 올려도 캐시가 유지된다.

| 단계 | 구성 | 언제 |
| :- | :- | :- |
| L0 | Sonnet 5.5 medium | 테스트·컴파일로 완전히 판정되는 작은 작업 (이름 변경, 컴파일 오류 수정, 단일 파일) |
| L1 (기본) | **Sonnet 5.5 low** | 일반 작업. 사용자가 결과물을 직접 피드백하므로 빠르게 나온 결과를 받아 고치는 흐름 (사용자 결정 2026-10-18, 토큰 분석 token-usage-2026-10-18.md 근거) |
| L1 재시도 | 같은 세션에서 effort 한 단계 올려 1회 (오염됐으면 새 세션) | 실패 요약이 원인을 분명히 가리킬 때 |
| L2 | Opus 5.5 medium, **새 세션** (원 과제 + 실패 요약 + 이전 시도 요약) | L1 2회 실패 / 같은 오류 반복 / 빌드·테스트 출력 없이 완료 보고 / 조기 종료. **기존 버그 수정과 프로필이 "처음부터 L2" 로 지정한 작업(예: 네트워크 동기화)은 처음부터 L2** |
| L3 | Opus 5.5 high | L2 실패 |
| 중단 | 매니저가 태스크 분할·acceptance 를 다시 본다 | 총 3~4회 시도, 또는 비용이 평소의 5배 초과 |

- 금지: **Haiku 는 우리가 지정하는 어떤 곳에도 쓰지 않는다** (워커·서브에이전트·테스트용 `claude -p` 포함. 사용자 결정 2026-10-17, 근거 findings.md "Haiku 5.5" 절), 같은 모델·effort 로 3회 이상 반복, max effort. (Sonnet low 무인 구현 금지는 2026-10-18 사용자 결정으로 해제 — L1 기본이 Sonnet low.)
- **모델·effort 는 환경이 정한다 (2026-10-25):** `harness.config.json` 의 단계표 + `hooks/launch-guard.mjs`(PreToolUse 훅)가 `start_session`·`Agent` 호출 때 태스크의 `level` 을 읽어 model/effort 를 덮어쓰고 `harness/ledger.jsonl` 에 기록한다. 단계를 바꾸려면 `tasks.json` 의 `level` 을 바꾼다. 제목에 태스크 ID(`T번호`)를 꼭 넣는다 — 없으면 기본 L1.
- (이전 규칙) **`start_session` 에 `model`·`effort` 를 항상 명시한다. 미지정 금지** — 미지정이면 앱 기본값 Opus 로 돈다 (2026-10-18 실측: T27~T39 13개가 미지정으로 전부 Opus 가 되어 5시간 한도를 소진).
- 브리프에 넣을 문구: "완료 전에 acceptance 의 check 를 직접 실행하고 출력으로 확인한다. 통과하면 멈춘다."
- 시도마다 `tasks.json` 의 그 태스크 `attempts` 에 `{level, model, effort, worker, result, note}` 를 매니저가 추가한다.
- **A/B 기간 종료 (2026-10-18)**: 사용자가 L1 을 Sonnet low 로 고정했다. 새 태스크는 `ab-log.md` 에 기록하지 않아도 된다(기존 기록은 보존). 재시도·승격은 위 사다리를 따른다.

## 3-2. 토큰 절감 규칙 (근거: findings.md "토큰 절감 (5.5 세대 전용)" 절)
5.5 는 캐시 읽기가 입력가의 0.05배라, 캐시를 한 번 놓치면 적중할 때보다 20~25배 비싸다.
- **세션 중 모델을 바꾸지 않는다.** 다른 모델이 필요하면 새 세션을 띄운다(사다리 L2 이상). effort 는 바꿔도 캐시가 유지된다.
- **모든 워커가 같은 앞부분을 쓴다:** 같은 프로젝트 CLAUDE.md(짧게), 같은 MCP 구성. 워커마다 다른 내용(태스크·실패 요약)은 **브리프 본문(첫 메시지)** 에만 넣는다.
- **태스크가 바뀌면 새 세션.** 같은 세션에서 `/compact` 로 이어 가지 않는다. 인계는 progress.md·result_spec 으로 한다. 1시간 넘게 쉰 워커는 다시 깨우지 말고 새 세션으로 띄운다.
- **스크린샷은 품질을 해치지 않는 선에서만 줄인다 (2026-10-18):** 같은 화면 반복 캡처 금지, 존재·위치·값처럼 수치로 확인되는 것은 `execute_luau` 로 읽는다. 시각 품질 판단이 필요한 검증은 그대로 스크린샷을 쓴다. 이미지가 쌓여 매니저 맥락이 40만 토큰을 넘으면 컴팩션하거나 인계 노트로 새 매니저 세션을 띄운다.
- **워커에게 보낼 메시지는 묶어서 한 번에 보낸다** (쉬는 워커를 여러 번 깨우면 매번 캐시를 놓친다).
- 자동 압축 창(`autoCompactWindow`)은 워커 200K~300K 가 권장값이지만 문서가 아닌 추론이다. 실측 후 정한다(아직 설정 안 함).

## 4. 감시
- 폴링하지 않는다. 워커가 턴을 끝내면 앱이 보고(note)를 보내 준다.
- 워커가 질문하면 답할 수 있는 건 답하고, 사용자 결정이 필요한 건 사용자에게 묻는다. 사용자 승인을 전달할 땐 사용자 말을 그대로 인용한다.

## 5. 검증 (보고를 믿지 않는다)
- 워커 보고는 주장일 뿐이다. 매니저가 직접 확인한다:
  - 변경된 파일을 Read/Grep 으로 확인
  - 프로필의 "검증" 절 (게이트 결과 파일 확인, 플레이 검증)
- 성공 기준을 하나씩 대조한다. 미달이면 `status: "fail"` 로 돌리고, 3-1 사다리대로 다음 시도를 정한다. 같은 세션 재시도면 지적 사항만 짧게 묶어 한 번에 보낸다(SendMessage).
- **실패 원인 분류**: 실패 요약에는 원인 종류를 꼭 붙인다.
  - `하네스`: 브리프 누락·규칙 모호·게이트 부재처럼 우리 절차 탓 → 그 자리에서 SKILL.md 나 프로필을 고치고 `decisions.md` 에 한 줄 남긴다.
  - `분야`: 엔진 API·게임 로직 자체가 어려운 탓 → 경험 기록(5-1)에 남긴다.
  - `모델`: 같은 브리프로 상위 단계는 풀었음 → 3-1 사다리만 따른다.

## 5-1. 분야별 경험 기록 (Harness² 경험 라이브러리의 가벼운 버전, 2026-10-25)
- 태스크를 pass/fail 로 판정할 때마다 매니저가 `harness/experience/<분야>.md` 에 이어 쓴다. 분야는 태스크의 시스템 단위로 짧게 정한다 (예: `ui`, `combat`, `network`, `save`, `shop`). 태스크에 `domain` 필드로 적는다.
- 한 항목 형식 (2~3줄):
  `- [날짜 T번호 pass|fail] 통한 것/막힌 것 한 줄 — 근거: 커밋·로그 경로·게이트 결과`
- **근거 없는 교훈은 쓰지 않는다.** 추측·일반론 금지.
- 파일이 30항목을 넘으면 매니저가 겹치는 항목을 합쳐 줄인다 (오래된 근거는 커밋 해시만 남긴다).

## 5-2. 블라인드 비교 (선택, 판정 명령으로 판정이 안 되는 작업만)
- 대상: UI 배치·연출·문구·밸런스 체감처럼 `acceptance.check` 로 합격 여부가 안 갈리는 태스크. 컴파일·테스트로 판정되는 태스크에는 쓰지 않는다 (비용 2배).
- 방법: 워커 2명을 서로 다른 접근 지시로 각자 worktree 에 띄운다(같은 L1 구성). 끝나면 매니저가 결과물만(스크린샷·diff) 이름을 가리고 A/B 로 붙여 고른다. 고른 이유와 진 쪽에서 가져올 점을 경험 기록에 남긴다.
- 사용자에게 보여 줄 땐 두 안을 함께 보여 주고 매니저 추천을 붙인다. 진 쪽 브랜치는 사용자 결정 뒤 지운다.

## 6. 보고
- 사용자에게 태스크 단위로 짧게 보고한다: 무엇이 끝났는지, 어떻게 검증했는지, 남은 것.
- 한국어로 쓴다. 버튼·요약문도 한국어로 쓴다.

## 하지 않는 것
- 매니저가 몇십 분짜리 구현을 직접 하지 않는다 (작은 수정·검증·문서화는 해도 된다).
- 사용자에게 태스크를 직접 관리하라고 넘기지 않는다.
- 병렬 워커 (P3 전까지 쓰지 않는다. 예외: 5-2 블라인드 비교, 3절 worktree 예외).
